# Алгоритм MVP

1. `setup()` и `dailySync` читают обязательные входные листы и находят строки заголовков в первых 20 строках. `На уточнении` и `Интерфейс собственника` не участвуют в runtime.
2. Для каждой сделки до формирования выплат определяется структура: `Нет` в поле визуализатора означает два акта, ФИО — три акта. Проверяются инженер, визуализатор для трёх актов и тип визуализации.
3. Для каждой ожидаемой выплаты проверяется ровно одно активное правило, а для запрошенных развёрток — специальное правило и модель `Тамбов`.
4. Получатель сопоставляется по нормализованному ФИО и периоду действия на дату готовности либо дату расчёта. Требуется ровно одна действующая запись, поддерживаемая модель и заполненный грейд.
5. Москва использует стоимость проекта и процент; Тамбов — метраж и ставку работы/пакета. Бонус ремонта всегда использует стоимость проекта. База и ставка должны быть положительными, ставка обязана быть единственной.
6. Все ошибки сделки накапливаются. При наличии хотя бы одной причины весь набор её выплат отбрасывается, ID и причины выводятся через `console.warn`, а расчёт следующих сделок продолжается.
7. Успешно рассчитанная выплата получает внутренний статус `TO_PAY`, если дата готовности есть, иначе `PLANNED`. Диагностические выплаты не создаются.
8. Фонд округляется до рубля. При полном распределении долей остальные части округляются вниз, а первая получает остаток.
9. Слияние выполняется по детерминированному ключу. Неизменённая строка не записывается; внутренние `PAID` и `CANCELLED` сохраняются без изменений.
10. При записи статусы переводятся в русские значения. Checkbox оплаты разрешён только для внутреннего `TO_PAY`; успешная операция записывает `Выплачено` и дату выплаты.
11. `dailySync` возвращает число рассчитанных и записанных выплат, а также количество и массив `skippedDeals` с ID и всеми причинами.
